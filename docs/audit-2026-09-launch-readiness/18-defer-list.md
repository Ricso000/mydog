# 18 — What NOT to Build Before the Hungarian V1 Launch

These are P1/P2-shaped features the audit evidence supports deferring past the 60-day Hungarian public launch. For each: why it's safe to defer given what the audit actually found, and what (if anything) should still happen now to avoid boxing in a future build.

| Feature | Current state (evidence) | Why defer | What to do now instead |
|---|---|---|---|
| **EU cross-border transport** (formal, compliance-grade) | Report 04: 7 of 17 identity/traceability fields entirely MISSING (microchip number, rabies record, passport number, true DOB, per-dog verification, EU token); `is_transportable` is a bare marketing flag with no legal backing (04) | This is genuinely greenfield schema+process work (new tables/columns, a verification workflow, likely a legal/compliance review) — not something a 60-day HU-only launch needs, since domestic adoption doesn't require it | Nothing — just don't let `is_transportable` marketing copy imply more capability than exists; consider softening any "cross-border ready" claims in current marketing pages until this is real |
| **Breeder marketplace / private seller marketplace** | NOT_FOUND anywhere in the schema or UI — `partner_type` enum has no "breeder" or "private seller" category (03, 10) | Entirely different trust/liability model from a shelter-adoption marketplace; would need its own moderation, verification, and likely different legal terms | Nothing needed now |
| **UK / USA expansion** | Country dropdowns (`KutyakFilters.tsx`, partner registration) are hardcoded to 10 EU countries (04); no i18n/locale infrastructure was found in this audit (not separately tested, but no `next-intl`/`i18next` in `package.json` per report 01's full dependency list) | Different legal jurisdiction, currency, language, and (for the US) an entirely different animal-welfare regulatory landscape — clearly out of scope for a HU pilot | Nothing needed now |
| **Full booking engine** (for vets/groomers/walkers etc.) | NOT_FOUND — no `partner_services`, `pricing`, or `availability` table exists at all (10 §1); the only real per-partner detail is a static contact block (10 §4) | The service-provider *data model* is already broad enough (9 partner types) to support this later without a schema rework, but building actual booking/scheduling is a separate, large product surface not needed to launch an adoption marketplace | If service listings ship at all for V1, keep them to "browse + contact info," matching what already works (`/partners/[slug]`) — don't build booking logic prematurely |
| **Own logistics system** (in-house transport coordination) | `transport` exists only as one `partner_type` enum value (03) — i.e., a transport company can list itself as a partner, nothing more | Building an internal logistics/routing system is a large, separate engineering effort with no current demand signal in the product (zero transport-related code beyond the enum value) | Nothing needed now; if transport partners are onboarded, they operate exactly like any other listed partner today |
| **Advanced SaaS tooling for partners** (analytics dashboards, bulk import, CSV export, team roles with real permission tiers) | `partner_member_role` enum (`owner/manager/editor/viewer`) exists but is **never checked anywhere in the app** — a stored-but-inert field (05 §6, 12 addendum); no bulk import exists (05 §7); admin's own analytics are limited to 4 basic counts (13) | These are real product-maturity features but not needed for a first cohort of a handful of shelters each managing a small number of dogs by hand | Don't build a permissions UI on top of `partner_member_role` yet — but also don't remove the column; it's harmless as-is and correctly not exposed to any privilege-escalation risk itself (12 addendum confirms `partner_members` has no self-service UPDATE policy) |
| **Advanced science publishing** (research articles, university/researcher profiles) | Confirmed **entirely absent** — zero code, zero schema, zero copy anywhere (11 §3) | This is a content-heavy, credibility-dependent feature area with no current infrastructure to build on (no CMS of any kind exists in this app — even the Kids content is hardcoded JSX, 11 §1) | Nothing needed now |
| **Large Kids content library** (many stories, real quizzes, downloadable teacher materials) | The existing `/gyerekeknek` page's interactive elements (story-reading, quiz, matching game, coloring download, drawing-contest entry, teacher-materials download) are all non-functional placeholder buttons with zero backing logic (11 §1) | Building out real interactive content is a content-production effort, not core to an adoption marketplace's launch | Recommend either (a) quietly removing/graying the non-functional buttons so the page doesn't imply broken functionality, or (b) leaving as aspirational static content — but don't invest in building the real interactivity pre-launch |
| **Mobile app** | NOT_VERIFIED as in-scope for this audit (a web-only Next.js app was audited); `/bobilos-utazas` has non-functional "App Store / Google Play" buttons with no actual links (02 §1) | A native mobile app is a separate, large engineering track; the web app itself isn't yet feature-complete for V1 | Remove or clearly label the App Store/Google Play buttons as "coming soon" rather than leaving them as silently-dead links |
| **AI features** | Not mentioned or found anywhere in the current codebase | No current infrastructure or demand signal found in this audit to build on | Nothing needed now |
| **Full digital dog passport / EU future verification token** | Confirmed fully MISSING at the schema level — this is the single largest gap identified in report 04 (0 of the token-related fields exist, not even as a stub column) | This is speculative future-regulation scope, not something a 60-day HU consumer launch needs | If genuinely anticipated, the cheapest hedge is reserving column names now (e.g. adding nullable `microchip_number`, `rabies_vaccinated_at` columns during an unrelated migration) rather than building any workflow around them — but this is optional, not urgent |
| **Dog Club subscription membership** | Confirmed **zero** trace at any level — no table, column, route, or copy (09) | This is a monetization feature requiring a payment provider integration that doesn't exist yet at all (07); building it before the core adoption marketplace and partner-approval security issues are solid would be premature | See report 19/20 for sequencing — Club should follow, not precede, a working payment stack and a stable core marketplace |
| **Foundation donation flows** (one-time, recurring, virtual adoption, corporate, SZJA 1%) | Entirely NOT_FOUND/PLACEHOLDER at every level (07, 08) — the `donations`/`virtual_adoptions` tables are schema stubs with no reachable write path (RLS blocks even a determined attacker from writing to them) | Same reasoning as Club — no payment provider exists yet; donation flows also carry their own compliance considerations (tax-receipt requirements, SZJA 1% program registration) that are a separate workstream from the core marketplace | If donations are promised in V1 marketing copy (the "🎁 Támogathatsz" card on `/szolgaltatasok` currently is, per report 07/08), either build a minimal real version or remove the promise — don't launch with a visible, non-functional donation mention |
| **Service marketplace commission / partner Pro subscription / affiliate-insurance-commerce** | Confirmed NOT_FOUND at every level (07) | All three require a payment provider that doesn't exist yet, and none has any UI/schema presence today | Nothing needed now beyond noting these depend on the same payment-provider decision as Club/Foundation |

## One item that is *not* on this defer list, despite looking similar in shape

**The interactive European map on `/menhelyek`** (explicitly labeled "Interaktív térkép hamarosan" in the current UI, 10 §3) is arguably safe to defer on its own — but the underlying **real partner index/browse page it's supposed to replace is not**. Report 05/17 flags `/menhelyek` and `/partners/[slug]` as a launch blocker specifically because the *real, working* shelter-detail page exists but has no way to be discovered (no working browse/index page links to it, and the current static `/menhelyek` page's links 404). Defer the map; do not defer fixing the broken discovery path to the shelter pages that already work.
