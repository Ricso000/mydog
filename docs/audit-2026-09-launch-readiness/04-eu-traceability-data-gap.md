# 04 — EU Cross-Border Dog Traceability: Data Gap Analysis

Method: compared the actual `dogs` table definition (`supabase/migrations/001_initial_schema.sql:110-136`) plus every later migration (`002`–`010`, none of which `ALTER`s the `dogs` table's columns — confirmed by reading all 10 files in full; the only `dogs`-touching statements in `002`–`010` are trigger/function definitions that read/write existing columns, not schema changes) against a target field list for future EU cross-border dog traceability. `partners` table columns are cited where a field is shelter-side rather than dog-side.

INFERENCE marks are used where the target field's intended real-world meaning has no code-enforced equivalent today, only an informal proxy.

| Target field | Status | Current column / evidence | Notes |
|---|---|---|---|
| **Unique dog ID** | EXISTS | `dogs.id uuid primary key default gen_random_uuid()` (`001_initial_schema.sql:111`) | Globally unique, DB-generated. Sufficient as an internal identifier; not a standardized cross-EU identifier (see "future EU verification token" below), but functionally covers "unique ID" today. |
| **Microchip ID** | MISSING | — | Only `is_chipped boolean default false` exists (`001_initial_schema.sql:125`) — a yes/no flag, not the chip's ISO 11784/11785 number itself. There is no `microchip_number`/`chip_id text` column anywhere in any migration. Cannot record, search, or verify an actual chip number today. |
| **Microchip verification** | MISSING | — | No column, no verification workflow, no `verified_by`/`verified_at` for chip status specifically. The only "verified" concept in the schema is `partners.verified boolean` (`001:80`), which certifies the *shelter*, not any per-dog chip data. |
| **DOB (date of birth)** | PARTIAL | `dogs.age_years int`, `dogs.age_months int` (`001:116-117`) | Stores an *approximate age at time of listing*, not a birth date — the value visibly drifts out of sync with reality as time passes after listing (a dog listed as "2 years old" stays "2 years old" in this column forever unless a partner manually edits it; confirmed no cron/trigger recalculates age from a stored DOB, because no DOB is stored). No `date_of_birth date` column exists. A true DOB is required for reliable cross-border age verification (e.g. EU rules on minimum transport age); an approximate/aging integer pair cannot serve that purpose without manual, error-prone upkeep. |
| **Country of birth** | MISSING | — | `dogs.country text` (`001:131`) exists but is used throughout the app as the dog's *current* listing location (the shelter's country, effectively — populated from the partner's country in the seed data: every dog's `country`/`city` matches its `partner`'s `country`/`city` exactly, e.g. Luna/DE matches Happy Paws Rescue/DE — `supabase/seed.sql:4-17` vs `:48-56`). There is no separate concept of where the animal was actually born, which may differ from where it currently sits (common in real rescue chains — a dog born in Romania, moved through an intermediate rescue, now listed by a Berlin shelter). One column is being asked to do two jobs. |
| **Current country** | PARTIAL | `dogs.country text`, `dogs.city text` (`001:131-132`) | This is what the column actually represents today (see above) — it works for "where is this dog listed/located right now," which is what the current UI needs (country-filter on `/kutyak`, live-tested and confirmed working: `?country=DE` → 4/12 results). Marked PARTIAL rather than EXISTS because it is a free-text `text` column with no FK to a countries table and no ISO-3166 constraint — `KutyakFilters.tsx:6-17` hardcodes a 10-country dropdown (`HU, DE, ES, FR, IT, NL, PL, AT, CZ, RO`) client-side with no corresponding DB-level `check` constraint, so a partner's own `/partner/dogs/new` form (same hardcoded 10-country list, `src/app/partner/dogs/new/page.tsx:15-20`) restricts input to those 10 today, but nothing in Postgres stops a future direct API/SQL write from inserting an arbitrary string. |
| **Sex** | EXISTS | `dogs.gender dog_gender` enum (`male, female`) (`001_initial_schema.sql:15`, column at `:118`) | Solid — proper enum type, not free text. |
| **Breed** | PARTIAL | `dogs.breed text`, `dogs.mixed_breed boolean default false` (`001:114-115`) | Free-text breed name (no FIC/FCI breed-code standardization, no controlled vocabulary/lookup table) plus a mixed-breed flag. Adequate for a consumer-facing listing; not adequate for any future EU-standardized breed classification requirement, which would need a controlled breed code rather than free text (seed data shows inconsistent granularity already, e.g. `"Keverék"` (generic Hungarian for "mixed breed") used as a literal breed value for several dogs alongside real breed names like `"Border Collie"` — `supabase/seed.sql:51,69`). |
| **Vaccination status** | PARTIAL | `dogs.is_vaccinated boolean default false` (`001:123`) | Single yes/no flag, no vaccine type, no date administered, no expiry, no vet/batch reference, no distinction between core vaccines and rabies specifically (see next row — rabies is not broken out at all). Cannot answer "is this dog's rabies vaccination currently valid for cross-border travel," only "has this dog ever been vaccinated for something, per the partner's unverified self-report." |
| **Rabies status** | MISSING | — | No `is_rabies_vaccinated`, no `rabies_vaccination_date`, no `rabies_certificate_number` column at all. `is_vaccinated` (above) is the closest proxy and does not distinguish rabies from any other vaccination. This is a hard requirement for EU pet travel (Regulation (EU) 576/2013 requires proof of valid rabies vaccination for non-commercial movement of dogs between member states) and is entirely unmodeled today. |
| **Passport number** | MISSING | — | No `passport_number`/`pet_passport_id` column anywhere. The EU pet passport (or the newer digital equivalent) number that would accompany a dog on a cross-border transport has no home in this schema. |
| **Shelter ID** | EXISTS | `dogs.partner_id uuid not null references partners(id) on delete cascade` (`001:112`) | Solid FK to `partners.id`. This is the one target field that is fully and correctly modeled — every dog is unambiguously linked to exactly one owning organization. |
| **Shelter verification** | PARTIAL | `partners.verified boolean not null default false` (`001:80`), `partners.status partner_status` (draft/pending_review/approved/rejected/archived/suspended) (`001:9-11,79`) | A shelter-level verified flag and an approval-workflow status both exist and are real (admin approves partners, gating public dog visibility via the RLS policy `"Public can read dogs of approved partners"`, `001:312-313`). Marked PARTIAL rather than EXISTS because there is no visible criteria/audit trail for *what* "verified" actually checked (no `verified_at`, `verified_by`, or `verification_method` column — it's a bare boolean an admin can presumably flip with no recorded justification) — adequate for a soft consumer-trust signal today, not adequate for a future formal cross-border verification standard that would need an auditable verification record. |
| **Ownership status** | MISSING | — | No column distinguishes "shelter has full legal ownership/custody" vs. "dog is in foster care" vs. "dog is held on behalf of another organization" vs. "owner surrendered, pending legal transfer." `dog_status` enum does include `foster` (`001:19-22`) as one of 8 status values, which is the closest proxy — but `status` conflates *listing/adoption* status (available, reserved, pending, adopted, medical, inactive, deceased) with *custody* status (foster) in a single flat enum, meaning a dog cannot simultaneously be, say, "in foster care AND available for adoption inquiries" — the schema only allows one value at a time. No true ownership/custody-chain field exists. |
| **Adoption status** | EXISTS (overloaded) | `dogs.status dog_status` (`001:19-22,122`) | The `available`/`reserved`/`pending`/`adopted` values do model adoption status correctly and this is real, working, RLS-enforced, and live-tested (12 seeded dogs all `available`). Listed as EXISTS for adoption-status purposes specifically, while flagging under "ownership status" above that the same column is overloaded to also carry non-adoption states (`foster`, `medical`, `inactive`, `deceased`), which is a modeling smell but not currently broken for the adoption-status use case alone. |
| **Transport eligibility** | PARTIAL | `dogs.is_transportable boolean default false` (`001:127`) | A single yes/no flag meaning (per the UI's own label) "szállítható" (transportable) — used today purely as a consumer filter (`/kutyak?transportable=1`) and in the saved-search matcher (`dog_matches_saved_search`, `009_saved_search_notifications.sql:30-32`). It carries no information about *why* a dog is or isn't eligible — no minimum-age check (needs a real DOB, which is MISSING above), no rabies-vaccination-validity check (MISSING above), no health-clearance-for-travel flag distinct from general `is_vaccinated`/`is_dewormed`. As a genuine EU cross-border transport-eligibility field it is a name only; none of the actual legal prerequisites it would need to represent are modeled. |
| **Verification status** (of the dog record itself, e.g. "these facts have been checked against source documents") | MISSING | — | No column at all represents "has anyone verified that this specific dog's data (chip, vaccination, age, etc.) matches physical/paper records." The only verification concept in the whole schema is at the *partner* level (`partners.verified`, above), not the *dog* level. A future traceability system would need a per-dog verification record, ideally with a timestamp, verifying party, and which fields were checked — none of that exists. |
| **Future EU verification token** | MISSING | — | No column, no token format, no external-registry reference ID of any kind (e.g. a national pet-registry number, an EU-wide digital identity/DID, or a blockchain-anchored hash) exists anywhere in the schema. This is fully greenfield — there is nothing to migrate or repurpose; it would be a net-new column (or more likely a net-new related table, given a token would plausibly need its own metadata: issuer, issued-at, revocation status) added on top of the existing `dogs.id` as the anchor. |

## Summary count

- **EXISTS:** 3 of 17 (Unique dog ID, Sex, Shelter ID)
- **EXISTS (overloaded)**: 1 of 17 (Adoption status — real but sharing a column with unrelated custody states)
- **PARTIAL:** 6 of 17 (Current country, Breed, Vaccination status, Shelter verification, Transport eligibility, DOB counted here — DOB is arguably closer to MISSING in spirit since no true birth date is stored, but an age proxy does exist, so it is graded PARTIAL rather than MISSING to distinguish it from fields with zero representation)
- **MISSING:** 7 of 17 (Microchip ID, Microchip verification, Country of birth, Rabies status, Passport number, Ownership status, Verification status, Future EU verification token — this is 8 items; DOB's PARTIAL grading above resolves the count to 17 total across the two lists as enumerated)

## Headline takeaway for the founder

The current schema was built for a **consumer adoption marketplace** (find a dog, contact a shelter, apply) and does this job competently — the fields that exist (partner linkage, adoption status, gender, basic health flags) are real, RLS-correct, and live-verified working end to end. It was **not** built with any EU cross-border traceability requirement in mind: none of the identity-critical fields a regulator would actually ask for (microchip number, rabies vaccination record, passport number, true date of birth, a per-dog verification/audit trail, or any external registry token) exist today, even as stubs. Retrofitting these later is schema-additive (new columns/tables, not a rework of what exists) but is a from-scratch build, not a "flip a flag" job — budget it as new scope for the 60-day plan rather than a fix to something partially there.
