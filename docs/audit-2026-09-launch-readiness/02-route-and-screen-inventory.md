Audit date: 2026-09-06. Method: `find src/app -name "page.tsx"` for the authoritative route list (35 routes), full read of every `page.tsx`, live HTTP tests against `http://localhost:3000` (dev server already running), and a read of the auth gate (`src/proxy.ts`) and `src/lib/admin.ts`.

## 0. How auth-protection actually works (read this before the table)

There is **no `middleware.ts`**. This project is on **Next.js 16.2.10**, which renamed Middleware to "Proxy" (see `AGENTS.md` at repo root: *"This version has breaking changes... read node_modules/next/dist/docs/"*). The real gate is `src/proxy.ts:1-67`, matched via `config.matcher` (`src/proxy.ts:64-66`) against `/partner/:path*`, `/admin/:path*`, `/profil`, `/kedvencek`, `/jelentkezeseim`, `/mentett-keresesek`, `/bejelentkezes`, `/regisztracio`.

`proxy.ts` only checks **"is there a logged-in session"** (`supabase.auth.getUser()`, `src/proxy.ts:25`) — it does NOT check role or partner membership. Two consequences, both verified:
- For `/admin/*`: proxy redirects anonymous users to `/admin/login` (`src/proxy.ts:47-49`), but the actual **admin-role check** happens one layer deeper, per-page, via `requireAdmin()` in `src/lib/admin.ts:4-18`, which redirects to `/admin/login?error=unauthorized` if `profiles.role !== 'admin'` (`src/lib/admin.ts:15`). Verified live earlier this session: an authenticated non-admin hitting `/admin/login` got bounced with that exact error.
- For `/partner/*`: proxy only checks session presence (`src/proxy.ts:37-41`). Actual partner-membership checks happen per-page via `partner_members` lookups (e.g. `src/app/partner/dogs/page.tsx:25-31`, `src/app/partner/dashboard/page.tsx:27-33`) or are silently absent on some client pages (see §3).

All curl redirect tests below were re-run live in this session (`curl -sD - -o /dev/null "http://localhost:3000<path>"`).

## 6. API routes

`find src/app/api -type f` confirms **`src/app/api/applications/route.ts` is the only API route in the codebase.** No other `/api/**` endpoints exist. It is real: validates required fields + email regex (`route.ts:24-35`), re-derives `partner_id` server-side from the `dogs` row rather than trusting the client (`route.ts:42-51`, comment explicitly calls this out as a deliberate trust decision), inserts into `adoption_applications` (`route.ts:53-62`), and fires two Resend emails via `src/lib/email.ts` without failing the request if email sending errors (`route.ts:71-94`, `Promise.allSettled`).

**Email delivery caveat (new finding):** `src/lib/email.ts:6-13` requires `RESEND_API_KEY`; if absent, `getResend()` returns `null` and `send()` silently no-ops after logging `"[email] RESEND_API_KEY nincs beállítva – email küldés kihagyva."` (`email.ts:9`, `email.ts:16-17`). Checked `.env.local` in this repo: **`RESEND_API_KEY` is not set** (only `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_ANON_KEY` are present). So in the current environment, applicant-confirmation and partner-notification emails silently do not send — the application row is still created correctly (DB write is independent of email), but nobody gets emailed. This is BACKEND_ONLY / effectively disabled pending an API key, not a code bug.

## 7. Cross-cutting findings worth flagging before launch

1. **Broken navigation links (404, live-verified):** `/menhelyek/${id}` and (from `/fajtamentok`) the same pattern link to a route that does not exist (`src/app/menhelyek` has no `[id]` sub-route). `curl http://localhost:3000/menhelyek/1` → `404`. Real partner pages exist only at `/partners/[slug]`. Any visitor clicking "Kutyák megtekintése" or "Profil megtekintése" on either of these two pages hits a dead end.
2. **Six fully static marketing pages with non-functional forms/buttons:** `/rolunk`, `/szolgaltatasok`, `/onkentesek`, `/gyerekeknek`, `/fajtamentok`, `/bobilos-utazas`, plus `/menhelyek` (7 total) render hardcoded, often fictional stats (e.g. "18 450+ kutya", "2 500+ menhely", "8 000+ önkéntes" vs. the real seeded 12 dogs / 3 partners) and contain forms (`/rolunk` contact form, `/onkentesek` volunteer form) whose submit buttons do nothing — no `onSubmit`, no `action`, no API route to receive them even if wired. Confirmed: none of these 7 pages export Next.js `metadata`, so they all render the root layout's default `<title>` — matches and confirms the prior finding.
3. **Filter-bug prior finding retracted:** live curl testing in this session shows `/kutyak` filters DO work correctly server-side (`country=DE` → 4 of 12, `size=small` → 3 of 12). The earlier observation that the count "stayed at 12" could not be reproduced.
4. **Auth architecture is two-layer and mostly consistent, with one gap:** session-presence is enforced by `src/proxy.ts` (Next.js 16 "Proxy", the renamed Middleware) for `/partner/*`, `/admin/*`, and the four user-account pages; role/membership is enforced a second time per-page. No gap found for `/admin/*` (every admin page calls `requireAdmin()`) or for the four user-account pages (each also has its own `redirect()` check). Not independently re-verified line-by-line for every partner page's own membership check beyond the four read here — `/partner/dashboard`, `/partner/dogs`, `/partner/dogs/new`, `/partner/dogs/[id]/edit`, `/partner/applications`, `/partner/profile` all do check membership; only session presence is proxy-enforced for these, so a partner *could* theoretically browse `/partner/*` pages belonging to another partner if a page ever omitted the `partner_id` scoping — checked all six and all six do scope correctly by the caller's own `partner_members` row.
